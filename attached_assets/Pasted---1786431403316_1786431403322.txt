أكمل العمل من الحالة الحالية للمشروع ولا تبدأ من الصفر ولا تعيد بناء أو إعادة هيكلة المشروع.

المهمة الوحيدة الآن هي: إكمال إصلاح مسار ترجمة صفحات المانغا والتأكد من أنه يعمل فعليًا باستخدام نموذج Gemini متوافق مع Gemini API Free Tier.

مهم جدًا:

- لا تفحص المشروع كاملًا.
- لا تعدّل أجزاء لا علاقة لها بالترجمة.
- لا تعيد تنفيذ الإصلاحات السابقة التي تم إنجازها.
- لا تستهلك وقت/رصيد الخطة المجانية في شرح طويل أو عمليات غير ضرورية.
- اعمل فقط على الملفات والمسار المسؤول عن الترجمة.
- استمر من آخر نقطة وصل إليها العمل قبل انتهاء حصة Replit.

1. النموذج الأساسي المطلوب

المشكلة الحالية أن المشروع يستخدم أو يحاول استخدام:

"gemini-2.5-flash"

ولا أريد الاعتماد عليه كنموذج الترجمة الأساسي في هذا الاختبار.

استخدم بدلًا منه:

"gemini-2.5-flash-lite"

هذا هو النموذج الأساسي المطلوب للترجمة والاختبار لأنه:

- مستقر.
- يدعم إدخال الصور.
- مناسب للمهام عالية التكرار.
- أقل تكلفة واستهلاكًا.
- متوافق مع Gemini API Free Tier وفق توثيق Google الحالي.

لا تستخدم أي نموذج Deprecated أو Shut Down.

لا تستخدم:

- "gemini-2.0-flash-lite"
- "gemini-2.5-flash-lite-preview-09-2025"
- أي Preview model غير ضروري.

2. أضف/صحح قائمة النماذج

في إعدادات التطبيق، اجعل قائمة نماذج Gemini مبنية على نماذج Gemini API الفعلية، وليس أسماء نماذج من خدمة أخرى أو أسماء UI فقط.

يجب أن يكون:

"gemini-2.5-flash-lite"

موجودًا وقابلًا للاختيار، ويجب أن يكون Default Translation Model.

إذا كان هناك نموذج آخر حالي يدعم Gemini API Free Tier + image input + translation بشكل موثوق، يمكن إضافته كخيار ثانوي فقط بعد التحقق من توفره فعليًا من API.

لا تضف عشرات النماذج بشكل عشوائي.

الأولوية:

1. Free Tier
2. Image input
3. Stable model
4. مناسب للترجمة
5. أقل استهلاك ممكن
6. سرعة جيدة

3. استخدم مفتاح الاختبار الموجود في المشروع

يوجد متغير بيئي مخصص للاختبار:

"GEMINI_TEST_API_KEY"

استخدمه فقط أثناء الاختبار التشخيصي.

لا تعرض قيمة المفتاح.
لا تطبع المفتاح في logs.
لا تحفظ المفتاح داخل source code.
لا ترسله إلى الواجهة.
لا تستبدل مفاتيح المستخدمين به.

استخدم:

"GEMINI_TEST_API_KEY"

لإجراء اختبار ترجمة حقيقي واحد فقط إذا كان ذلك ضروريًا لإثبات أن مسار Gemini يعمل.

4. لا تستهلك Free Tier

هذه نقطة حرجة جدًا.

لا تقم باختبار عدة صفحات.
لا تقم بترجمة فصل كامل.
لا ترسل نفس الصورة أكثر من مرة.
لا تجرب عدة نماذج بشكل عشوائي.

استخدم صفحة مانغا واحدة فقط موجودة بالفعل في مسار الاختبار الحالي.

اختبار واحد فقط يكفي لإثبات:

Image → Gemini API → OCR/translation result → parser → renderer.

إذا نجح "gemini-2.5-flash-lite"، توقف عن الاختبارات ولا ترسل طلبات إضافية.

إذا فشل الطلب، لا تكرر الطلب تلقائيًا.

سجّل السبب الدقيق أولًا.

5. فحص مسار الترجمة

افحص فقط هذا المسار:

Reader
→ page image
→ native image/cache
→ translation service
→ Gemini request
→ response
→ JSON/parser
→ translation regions
→ rendering

حدد بالضبط أين يفشل.

يجب التفريق بين:

1. Image acquisition failure
2. Gemini API request failure
3. Invalid API key
4. Model not found
5. Model unavailable
6. Free-tier quota/rate-limit
7. HTTP error
8. Empty response
9. Invalid Gemini response
10. JSON parsing failure
11. Rendering failure

لا تعرض للمستخدم رسالة عامة مثل:

"Failed to fetch"

إذا كان الخطأ الحقيقي هو Gemini API أو model/quota.

6. اختبار Gemini الحقيقي

بعد التأكد من أن الصورة تصل بشكل صحيح إلى خدمة الترجمة:

استخدم:

"GEMINI_TEST_API_KEY"

مع:

"gemini-2.5-flash-lite"

وأرسل صفحة واحدة فقط.

استخدم أقل Prompt ممكن مع الحفاظ على صحة الترجمة.

لا تستخدم thinking/reasoning غير ضروري.

إذا كان النظام الحالي يستخدم:

"thinkingBudget"

فاضبطه على أقل قيمة مناسبة للمسار الحالي، وخصوصًا لا تجعل النموذج يقوم بتفكير مطول أثناء اختبار الترجمة.

الهدف هو اختبار الاتصال والترجمة، وليس اختبار قدرات reasoning.

7. لا تغيّر Architecture

لا تستبدل نظام الترجمة بالكامل.

لا تضف backend جديدًا.
لا تضف proxy جديدًا إذا كان الموجود يعمل.
لا تغير ImageLoader إلا إذا أثبت الاختبار أن المشكلة فيه.
لا تغير نظام API keys بالكامل.
لا تغير واجهة التطبيق إلا بالقدر الضروري لإظهار النموذج الصحيح أو الخطأ الصحيح.

استعمل البنية الموجودة حاليًا.

8. التحقق من النموذج قبل إرسال الطلب

قبل إرسال طلب Gemini، تحقق برمجيًا من أن النموذج المستخدم فعليًا هو:

"gemini-2.5-flash-lite"

وسجل فقط:

MODEL = gemini-2.5-flash-lite
KEY = PRESENT
IMAGE = PRESENT
REQUEST = START

ثم بعد الطلب:

HTTP_STATUS
RESPONSE_TIME
RESPONSE_PRESENT
PARSE_SUCCESS

ممنوع تسجيل قيمة API key.

9. إذا نجح الاختبار

إذا نجحت ترجمة الصفحة باستخدام:

"gemini-2.5-flash-lite"

فاجعله النموذج الافتراضي للترجمة.

واجعل إعدادات الترجمة تستخدمه فعليًا في:

- single page translation
- chapter translation
- أي translation queue موجودة

مع الحفاظ على اختيار المستخدم إذا اختار نموذجًا آخر متاحًا.

لكن لا تغيّر النموذج تلقائيًا بعد نجاح الاختبار.

10. إذا فشل gemini-2.5-flash-lite

لا تبدأ بتجربة نماذج كثيرة.

حدد سبب الفشل أولًا.

إذا كان:

401/403 → مشكلة API key أو صلاحيات.

404/model not found → اسم النموذج أو API endpoint خاطئ.

429 → Free Tier quota/rate limit.

5xx → مشكلة مؤقتة من Google.

Network/fetch → مشكلة اتصال وليس نموذج Gemini.

Invalid response → مشكلة parsing/request format.

إذا كان النموذج نفسه غير متاح على المفتاح، لا تكرر الطلب.

افحص قائمة النماذج المتاحة للمفتاح إن كانت API تسمح بذلك، ثم اختر أقرب نموذج مستقر مجاني يدعم الصور.

11. النتيجة المطلوبة

لا تقل لي فقط:

"تم الإصلاح".

أريد في النهاية تقريرًا قصيرًا جدًا يوضح:

- السبب الحقيقي للفشل.
- الملف/الملفات التي تم تعديلها.
- النموذج الذي تم اختياره.
- هل "gemini-2.5-flash-lite" نجح أم لا.
- هل تم تنفيذ ترجمة حقيقية لصفحة واحدة.
- نتيجة الاختبار.
- هل بقيت مشكلة أخرى.

الأهم:

لا تعيد فحص المشروع كاملًا ولا تبدأ من البداية. أكمل من الحالة الحالية، أصلح فقط مسار الترجمة، واستخدم اختبار Gemini واحدًا فقط لتأكيد النتيجة.
